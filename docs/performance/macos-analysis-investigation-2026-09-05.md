# macOS 分析耗时调查（2026-09-05）

调查基线：`fix/analyzespeed`，提交 `8f9bb7bddeae3dd942d11d54c2dd80c2470bc645`。调查开始时工作树干净。本次只增加调查报告；计时用的 Worker 副本及结果放在本地忽略目录，不修改生产实现、模型或用户历史记录。

## 结论与证据边界

两段本地历史视频的前 150 帧实测显示，当前 Core ML 预测调用占 Worker 内部总耗时约 86%–90%（第二次运行）。优先研究模型推理精度、执行配置和输入形状，其次研究有界流水线；单纯增加 CPU 线程不太可能大幅缩短这两段样本的分析耗时。

这是短片段的实际运行证据，不是整片性能、热稳定性或识别准确率验收。未确认用户截图对应哪条历史记录；截图中的 Worker 在调查时已经退出，不能回溯该瞬间的 GPU 时间线。预测调用耗时包含 Core ML 内部调度与同步，不能等同于纯 GPU kernel 时间。

进程 CPU 40.7% 可近似理解为 0.407 个逻辑核心的平均执行时间，不是固定只使用某一个核心，也不代表异构 CPU 算力的精确占比。系统 CPU 空闲比例不能直接换算成分析加速倍数。GPU 86.7% 表示该采样期较忙，不能证明计算单元、带宽、频率或整个分析阶段均达到上限。

## 当前实现

- Mac 分支走 Electron → 原生 Swift Worker → Core ML；此次测量不涉及 Python/CUDA 路径。入口见 `src/main/macos/analysis.ts` 与 `src/main/macos/client.ts`。
- BlurBall 使用 `.cpuAndGPU`；转换显式设置 `compute_precision=FLOAT32`，输入、输出均为 Float32，模型为 ML Program。见 `macos/Sources/Worker/main.swift:270`、`macos/scripts/convert_models.py:59`，已核对 `.runtime/macos/Models/BlurBall.mlmodelc/metadata.json`。
- Apple 文档说明，FP32 类型的 ML Program 不能在 Neural Engine 上运行；只把配置改为 `.all` 不会自动将其降为 FP16。FP16/混合精度需要另行转换，并确认设备分配。[Typed Execution](https://apple.github.io/coremltools/docs-guides/source/typed-execution.html)
- 全量模式按三帧一窗、步长三推理，保留三帧输出；解码 → 裁剪/归一化 → 拼接/复制输入 → 同步推理 → 热图解码，当前串行。`previous` 参与连续轨迹筛选，后处理有顺序依赖。
- 解码器与滤镜图各配置两线程，原生 reader 未配置 VideoToolbox 硬件解码。见 `macos/Sources/NativeBridge/TTNative.cpp:52`。线程数本身不是已确认瓶颈。
- 每窗有 Float 数组拼接和 MLMultiArray 复制，每输出通道重新分配热图与检测数组；存在优化空间，但当前测量中输入组装开销不到 Worker 总耗时的 1%。
- 两阶段模式先做同样数量的全片粗筛推理，再在候选区间逐帧滑窗精查；第二阶段仍解码、预处理全片，然后才判断是否在候选区间。见 `macos/Sources/Worker/main.swift:213`。
- Table 模型单独使用 CPU，转换脚本明确记载其匹配顺序对 GPU 浮点误差敏感。此次分析建议不直接扩展到 Table 模型。

## 测量方法及结果

机器：Apple M5，10 个 CPU 核心，16 GiB 内存，macOS 26.6.2（25G83）。

以当前源文件建立临时 Swift Package，release 编译。在副本中加入单调时钟分项计时，并让解码准备接口最多返回 150 帧。读取现有历史记录的原视频路径、原始时间戳与标定，调用现有编译模型，使用 `full` 模式及 0.7 阈值。每个片段运行两次，每次 50 次三帧预测。未清理系统模型缓存，因此第一次也不能称为冷启动测试。

不包含自动标定、VFR 转 CFR、Electron 界面、历史保存、导出以及进程启动前后的耗时。`worker_total` 从 Worker.run 入口计至退出；输入与推理合计是嵌套计时，不能再与推理时间直接累加。

## 建议实施顺序

### 1. 固定端到端基线与质量基线

补充低开销分项遥测：视频探测、标定、归一化、模型加载、解码、预处理、输入复制、预测、后处理、结果保存，记录真实 shape、预测次数、模式、候选区间覆盖率及整任务墙钟耗时。用 Core ML Instruments 和 Metal 时间线区分计算、同步等待与空隙；不能只看活动监视器百分比。

同一原片、标定、阈值和模式做优化前后对照。速度至少记录完整任务耗时、重复运行中位数和较长运行表现；准确率记录球可见性变化、坐标误差、落点事件、回合数量、起止边界及漏检。并发方案还应检查峰值内存、结果顺序、取消与恢复。

### 2. 优先实验 BlurBall FP16 / 混合精度

保留当前 FP32 模型作为对照，从同一 checkpoint 另行转换 FP16 模型，先保留 Float32 输入/输出以隔离接口改动。对比 FP32+CPU/GPU、FP16+CPU/GPU、FP16+ALL、FP16+CPU/Neural Engine，使用实际输入 shape。通过 MLComputePlan 或 Instruments 确认算子实际设备分配，不从 `.all` 字面推断全部硬件都参与。

FP16 是优先实验方向，尚未在本次调查中转换、测量或验收，不能承诺两倍或其他固定收益。特别关注阈值附近热图变化；像素误差小也可能改变连通域、可见性和回合边界。若全 FP16 不通过质量门槛，再定位需要保留 FP32 的算子。

不优先做 INT8、剪枝、重训练或替换模型；它们需要更多校准、质量数据与独立验证。

### 3. 不改模型语义的有界并行

将解码/预处理与预测重叠，先测试容量为 2–4 窗口的队列，限制内存并保留取消。预测并发度对比 1、2、4；采用 Core ML async 或 batch API，不直接从多个线程并发调用同一个模型的同步预测方法。返回结果必须按帧序交给依赖 `previous` 的后处理。

当前输入张量 batch 维固定为 1；使用多个独立输入的 Core ML batch API，与将张量改成 `[B,9,H,W]` 是两项不同实验，后者涉及模型形状契约。Apple 也要求对并发收益与峰值内存做实际 profiling。[Async prediction](https://developer.apple.com/videos/play/wwdc2023/10049/)

复用输入与热图缓冲可以一起研究，但先保持步长、三帧上下文、BGR 预处理、阈值和轨迹顺序不变。GPU 较忙时，更多 Worker 或更多预测未必更快；多视频吞吐率也不能替代单视频延迟指标。

### 4. 检查 shape 与 ROI，而不是盲目降低清晰度

当前 shape 使用较宽的 RangeDim；尝试对相同实际尺寸做固定 shape 或 EnumeratedShapes 转换，先测试编译优化带来的收益，不改变输入内容。Apple 对有限枚举形状提供专门优化支持。[Flexible Input Shapes](https://apple.github.io/coremltools/docs-guides/source/flexible-inputs.html)

`AnalysisROI` 保留了纵横方向约 1.25 倍的放大及 stride 对齐。缩小输入、移除放大或缩减 ROI 会改变小球像素尺度和覆盖范围，属于质量权衡，不能作为无损重构。第二段记录 ROI 覆盖全画面高度，仅凭数值无法判定标定错误；必须结合画面检查桌角和回合中球的活动范围。

### 5. 按模式处理剩余开销

两阶段不应被视为全量模式的天然加速开关。设全片 N 帧、精查覆盖 fN 帧，粗略预测次数由 full 的 N/3 变成 N/3+fN，即约为 full 的 1+3f 倍；这只是预测次数估算，不是整任务时间模型。

第二阶段可先跳过非候选区间的 ROI 仿射与归一化，保留区间首尾的三帧上下文；再评估关键帧 seek 和精确解码。当前 reader seek 会按时间估算 frame index，直接拿来跳段可能改变 VFR 帧身份，必须同时验证 PTS、全局帧号、边界重复帧和轨迹重置。

硬件解码或增大解码线程在 4K/8K/HDR 等解码重任务上另做基准。目前两段 SDR 小样本不足以证明值得优先改造该路径。自动标定和 VFR 归一化未纳入本次计时，若整任务慢在这些阶段，应重新按端到端分项占比排序。
