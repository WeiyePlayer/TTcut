# DirectML 实际推理失败：第二次日志诊断与修补

## 已确认的问题

输入为用户提供的 `logs-260928-1.zip`；本次没有石墨文档链接或原视频。
`40ef37b8-898e-4142-89d6-cecb7c0ed330.log` 显示第一次会话复用补丁已经生效，
但实际执行模型时仍报错。以下时间为日志 UTC：

| 时间 | 事件 |
| --- | --- |
| 00:00:27.242 | 开始分析，手动标定，原始 VFR，不执行 CFR 转码。 |
| 00:00:33.718 | `704x264, batch=16` 探测成功。 |
| 00:00:33.736 | 正式 `provider=directml`。 |
| 00:00:36.676 | `session.run` 抛出 `UnicodeDecodeError`，包装为 `DirectML inference failed`。 |
| 00:00:36.683 | 整任务回退 CPU。 |
| 00:00:37.631 | `provider=cpu, batch_size=4`。 |
| 00:51:03.385 | 28,592 帧预测完成。推理 2708.057 秒，预测总计 3025.752 秒，9.450 FPS。 |
| 00:51:05.707 | 结果保存，82 个回合。 |

整任务耗时 3038.465 秒（50 分 38.465 秒）。推理占预测阶段的 89.50%，其余
解码、预处理和轨迹处理合计约 317.695 秒。首要瓶颈是 GPU 失败后 CPU 推理；
2.36GB 文件大小并不能解释为什么切换到了 CPU。导出 28 段全部退出码为 0，
约 61.66 秒完成，本次没有针对导出修改代码。

## 原因能够确定到哪里

确定：错误发生在 DirectML 原生执行 `session.run`，随后应用立即重启 CPU 分析。
第一次补丁只解码会话初始化异常，因此这次运行异常的原始文本仍被 UTF-8
解码错误遮住。不能把它解释成视频损坏、中文路径错误，也不能确认具体 HRESULT。

本机对照发现：动态输入、batch=16 在 8GB RTX 4060 Laptop 上既慢又接近显存
容量上限；固定任务输入尺寸且 batch=4 大幅降低显存占用并提高吞吐。这支持
“大批量导致资源压力”的解释，但用户显卡型号/显存和原生错误未知，因此仍是
用户故障的候选原因，而非已经证实的显存不足诊断。

## 修补

- DirectML 默认 batch 从 16 降为 4，可降至 2、1；CPU 仍为 4。
- 通过 ORT 的 free-dimension overrides，在创建 DirectML 会话时固定本次任务
  的 batch、height、width。模型权重、FP32、输入分辨率和识别阈值不变；仍关闭
  已知不兼容的 ORT 图优化。CPU/球桌模型不应用这些维度覆盖。
- 探测由一次改为三次连续执行，切换输入缓冲内容；复用成功会话，不能只凭
  一次暖启动就认为实际推理可靠。
- 真正推理失败时，只对尚未完成的窗口按 4→2→1 在 GPU 上重试。退出异常
  处理并释放旧会话后再创建新会话，避免异常回溯持有旧显存。已成功的窗口不
  重复提交轨迹，不丢帧、不改变时间戳或顺序。
- 记录并缓存成功缩小后的批量，后续批次继续使用该批量；仅在最小 GPU 批量
  也失败或遇到不可重试错误时，由原有外层保护整任务重启 CPU。
- 初始化和实际推理异常均保留 Windows 原生错误文本，实际推理还记录输入形状。
- 升级探测缓存标识，旧版本的一小时 CPU 失败标记不会阻止新配置重新尝试 GPU。

固定输入维度的依据是前次已核对的
[ONNX Runtime DirectML 性能说明](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html#performance-tuning)。

## 实测

环境：本机 RTX 4060 Laptop，8188 MiB 显存，随包 Python 3.12.13 /
ONNX Runtime DirectML 1.24.3。测试使用本机真实乒乓球片段的前 8 秒，缩放至
1920×1080，共 239 帧，沿用用户 ROI 尺寸使模型输入为 704×264；这不是用户原视频。
两种配置在独立进程中串行执行，模型、视频、ROI、阈值相同。

| 指标 | 旧安装包配置 | 新配置 |
| --- | ---: | ---: |
| GPU batch | 16 | 4 |
| 输入维度 | 动态 | 创建会话时固定 |
| 加载/探测 | 5.620 秒 | 1.274 秒 |
| 预测阶段 | 17.514 秒 | 4.044 秒 |
| 其中推理 | 15.669 秒 | 2.272 秒 |
| 加载＋预测 | 23.135 秒 | 5.319 秒 |
| 显卡总显存采样峰值 | 7737 MiB | 3423 MiB |
| 239 帧中可见/缺失 | 92 / 147 | 92 / 147 |

本机该片段加载＋预测约为原来的 23%，即约 4.35 倍速度。显存通过 nvidia-smi
每 0.5 秒采样，包含整个显卡的其他进程，不是 TTcut 单进程精确峰值。
测量范围是模型加载和完整预测链，不含 Electron、回合后处理或历史保存。

逐帧比较：帧号、时间、可见性、球坐标、来源、时间来源全部相同；82 帧的
浮点置信分数有微小差异，最大绝对差为 0.0000915527。不是逐位浮点完全相同，
也不构成用户视频的识别准确率验收。

另在新配置的真实视频第二个推理批次注入可恢复异常：自动从 batch=4 降到 2，
仍使用真实 DirectML 完成全部 239 帧，耗时 5.356 秒，未回退 CPU。全部轨迹字段
与正常新配置完全相同。该故障是人工注入，不是复现了用户的原生驱动错误。

## 后续复测判据

日志应显示 `batch=4, fixed_shape=true, runs=3`，正式分析为 `provider=directml`。
如果运行中必须缩小批量，应出现 `DirectML recovered on GPU`，而不是立即重启
CPU。若最小批量仍失败，新增 `Native error` 和输入形状用于判断具体驱动/
资源错误，再决定是否需要更换驱动或其他针对性处理。
